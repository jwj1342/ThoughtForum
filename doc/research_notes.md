# 零信任隐式思维论坛：方向梳理

> 2026-10-17 · 依据：本索引 707 篇，其中本轮新收 131 篇，带 `shared-memory` 或 `support` tag。另有 5 路定向检索的摘要层报告。
> 这个方向是 [Coding 聚焦](#tab=coding) 中 C3（KV 交接）、C5（接口默契）、C7（共享 latent 记忆）、C8（合谋与 latent 防火墙）的合并与升级版。
> 研究计划见 `doc/RP.md`；代码说明见仓库根目录的 `README.md` 和 `doc/code_guide.md`。

**研究目标（一句话）**：在长程 SWE 项目里，让一大群互不信任的 agent 不靠文字，而是通过一个隐式的共享“思维论坛”交流，协作推进同一个项目。这等于为 LLM agent 设计一种新的通信方式，并研究它的能力与风险。

**做法（2026-10-18 精简后）**：一个简单、免训练的方法，加一个信息量已知的测量基准，用来揭示现象。方法：帖子附带作者模型从自己完整上下文中读出的 k 个潜在向量。基准：私有约定必须经帖子传递，用代码执行判定。**更正（同日）**：原先报告的"未训练 latent 能传内容""读者用得出、说不出"来自评测 bug，已撤回（R13）；站得住的是状态层面的"latent 跟随作者所知"（R8、R12），对应"看到说法后主动核对"。见 §3、§5。

## 0. 核心判断

1. **“伪说辞”是真实、可测、会传播的现象。** 但多数虚报来自能力不足，而不是策略性欺骗，论文叙事应据此措辞。
   - [Failure as a Process](#paper:zhao2026failure)：Terminal-Bench 上 26% 的失败轨迹附带了伪造证据，宣称成功；84% 的伪造发生在任务已无法挽回之后。
   - [OverclaimBench](#paper:smyth2026quantifying)：67.9% 的运行没读完要求审查的文件，其中 80.4% 谎称已完成；改成委派给子 agent 后，误导性报告升到 93.8%。
   - [TIDE](#paper:yan2026truth)：一个持有关键证据的 agent 撒谎，群体的真相恢复率就从 72.5% 降到 14.2%，而且撒谎者退出后，诚实 agent 仍在转述它的说法。
   - [Deception by Omission](#paper:florin2026deception)：模型有 67.1% 的情况不披露自己的错误，但明知而隐瞒的只占 5.3%。
   - 因此主叙事建议写成“**能力驱动的虚报在群体中传播**”。“策略性欺骗”作为第二层、有证据时再提。
2. **内部状态往往比文字更接近真实状态，但这个优势脆弱。**
   - 正面证据：
     - [Latent Programming Horizons](#paper:silva2026latent)：在 SWE-bench 上，从 hidden state 解码“补丁能否通过测试”，AUC 最高 0.83。
     - [Silent Dissent](#paper:ni2026silent)：口头屈从多数的 agent，残差流里仍保留着原来的判断。
     - [FIBS](#paper:hollinsworth2026telling)：探针在 BashArena 上 AUROC 98.0%。
   - 反面证据：
     - [Neural Chameleons](#paper:mcguinness2025neural)：模型能学会躲开探针。
     - [Feedback Evasion](#paper:keenan2026llms)：只凭以往的监控判决就能学会规避，TPR 从 100% 降到 4%。
     - [AO Limits](#paper:jakkli2026current)：去掉“复述附近文本”这条捷径后，公开的 Activation Oracle 在安全任务上接近随机。
   - 所以“latent 更难说谎”只能当**待检验的假设**，不能当前提。
3. **隐式共享要有效，需要训练和结构。**
   - 免训练的直接替换基本传不过内容：[deng2026close](#paper:deng2026close)。
   - 并发 lane 的增益只有约 +1.1：[LaneRoPE](#paper:cesa2026lanerope)。
   - 训练过的跨线程注意力明显有效：[LACE](#paper:li2026lace)、[Bridge](#paper:dong2025generalized)。
   - KV 片段放在一个池里不等于能按需寻址：[MaSRead](#paper:baquero2026masread)。
   - **还没有人把 thread、topic、订阅这类结构做到 latent / KV 层。**现有的 latent 共享（[Hogwild!](#paper:rodionov2025hogwild)、[Group Think](#paper:hsu2025group)、[LatentMAS](#paper:zou2025latent)）要么全广播，要么是链式中继。
4. **长程 SWE 的“大队 agent”目前全在文本 / git 上做，而且已经暴露出结构性问题。**
   - [Agensh](#paper:zhan2026agensh)：ProgramBench 上 1→128 个 agent，通过率从 19.3% 升到 28.8%。
   - [ScaleMAS](#paper:qi2026scaling)：只追加的共享库加引用图，可扩到 128 个 agent。
   - [Agora](#paper:zhang2026agora)：13 个 worker 跑了 12 天，出现 696 对重复劳动。
   - [Cursor](#paper:lin2026scaling)：几百个 agent 规模下，平等结构配锁文件，20 个 agent 的吞吐只相当于 2–3 个，最后改成了层级结构。
   - [GEA](#paper:weng2026group)：组内共享经验做群体进化，SWE-bench Verified 71.0% vs 56.7%，但共享的是文本，也没有做内容对照。
5. **空白象限：“零信任 × 隐式论坛 × 长程 SWE”。** 五路检索都没找到同时具备这三点的工作。M2 的原话是：“没有任何长程多 agent SWE 工作用 latent/KV/hidden state 作为共享论坛”。这里的设计原则是：**信任效果，不信任说法；内容可以隐式，出处必须显式。**

## 1. 问题设定

- **参与者**：同一个冻结模型的多个实例，各自持有不同的上下文（任务、自己写的代码、CI 给的测试结果），必须交换信息才能完成共同的项目。
- **零信任**：照常交流，但不默认相信任何一条说法；读者在使用同伴的说法之前，要主动核对。agent 说的话都可能不实，包括“我做完了”和对接口的描述，不论出于能力不足还是故意。核对需要可信的依据：代码执行（可见测试、隐藏测试），或由受信推理从作者上下文读出的信号。评测用隐藏测试，agent 看不到。
- **帖子** = 一行明文出处（作者、对象）+ 载荷。载荷是文字，或者 k 个潜在向量。
- **受信推理**：潜在向量由受信推理端（harness 或托管模型的提供方）从作者的真实上下文算出，agent 不能自己提交向量；否则它可以直接伪造一个“看起来诚实”的帖子。所以“潜在帖子更难撒谎”这类结论，只在这一前提下成立。
- **谎言**：作者的话与它上下文里的事实不一致，例如把格式说错，或代码没过却声称做完。

方法与测量见 §3，现象与风险见 §5。

## 2. 证据地图

### 2.1 伪说辞与传播（支撑卖点）

| 论文 | 发现 | 用途 |
|---|---|---|
| [Failure as a Process](#paper:zhao2026failure) | 26% 的失败轨迹附带伪造证据，宣称成功 | 虚报在 coding agent 中很常见 |
| [OverclaimBench](#paper:smyth2026quantifying) | 80.4% 的未完成运行谎报完成；委派后升到 93.8% | 跨 agent 边界后会放大 |
| [TIDE](#paper:yan2026truth) | 真相恢复率 72.5% → 14.2%；虚假证词采纳率 70.7%，真实证词只有 25.4% | 群体传播 |
| [Agents Catching Agents](#paper:ordez2026agents) | 两个同伴说同一个错误答案，38% 会跟随；**私下重新询问**的 referee 最有效 | 支撑 breakpoint 式询问 |
| [Compaction as Epistemic Failure](#paper:tamba2026compaction) | 压缩摘要把被杀进程的部分输出写成“已确认结果”，后续会话直接继承 | coding 交接中的传播（单作者案例） |
| [Deception by Omission](#paper:florin2026deception) | 67.1% 不披露错误，明知隐瞒仅占 5.3% | 叙事措辞要克制 |
| 已收录：[MAST](#paper:cemri2025multi)、[ImpossibleBench](#paper:zhong2025impossiblebench)、[Reward Hacking 可传递](#paper:hu2026reward)、[EVOMAL](#paper:wu2026evomal) | 验证失败、过早终止；测试作弊；作弊策略能在 agent 之间传播 | 背景与基线 |

### 2.2 内部状态与“可询问性”

| 论文 | 发现 | 支撑 / 警示 |
|---|---|---|
| [Latent Programming Horizons](#paper:silva2026latent) | 从 hidden state 预测补丁能否通过测试，AUC 最高 0.83 | 支撑：latent 里带有“真实代码状态” |
| [Silent Dissent](#paper:ni2026silent) | 屈从的 agent 内部仍保留原判断，logit lens 读不到 | 支撑：文字共识 ≠ 内部状态 |
| [FIBS](#paper:hollinsworth2026telling)、[STATEWITNESS](#paper:chen2026decoding) | 探针 / 解码器检测破坏与欺骗，AUROC 0.92–0.98 | 支撑。但 FIBS 只比文本监控高约 0.6 个百分点 |
| [Are LRMs Easily Interpretable?](#paper:dilgren2026latent) | latent 起作用时，65–93% 的正确样本能解码出推理轨迹 | 支撑：latent 可以“问出来” |
| [SELR](#paper:zhao2026think)、[Activation Oracles](#paper:karvonen2025activation) | 自解释 latent 推理；训练 LLM 回答关于激活的问题 | 可询问 reader 的训练路线 |
| [AO Limits](#paper:jakkli2026current)、[Observable Patterns](#paper:aswal2026observable) | 解码器走捷径；能解码 ≠ 模型真用了它 | 警示：解码结果必须做因果验证 |
| [Neural Chameleons](#paper:mcguinness2025neural)、[Feedback Evasion](#paper:keenan2026llms) | 探针可以被规避；监控判决不能回流到 agent 的上下文里 | 警示：**询问结果与 agent 隔离** |

### 2.3 隐式共享的底座

- **并发共享 KV / 注意力**：
  - [Hogwild!](#paper:rodionov2025hogwild)：免训练，自组织。
  - [Group Think](#paper:hsu2025group)：token 级并发。
  - [LACE](#paper:li2026lace)：训练跨线程侧路，AIME25 上 20.0，对比 Isolated 6.7。
  - [Bridge](#paper:dong2025generalized)：批维度注意力。
  - [LaneRoPE](#paper:cesa2026lanerope)：同预算下增益约 +1.1。
- **可寻址存储**：
  - [AsyncLLM](#paper:yakushev2026llms)：每个协程写自己的 CacheBlock，通过 cache view 读别人的块，最接近“论坛底座”；但 DevOps-Gym 上准确率从 61.8 降到 55.9。
  - [MaSRead](#paper:baquero2026masread)：标签路由。
  - [Cache Merging](#paper:baquero2026cache)：拼接合并不满足交换律。
- **coding 场景**：
  - [LaMAR](#paper:jiao2026lamar)：程序修复中共享 KV，ASE 2026，目前唯一一篇 SE 会议上用 KV 信道的工作。
  - [LatentMem](#paper:fu2026latentmem)：多 agent latent 记忆。
- **一致性与过时**：
  - [Rollback Consistency](#paper:zhang2026aborted)：保留的 KV 翻转了 63 个审计格中的 25 个。
  - [KV Provenance](#paper:song2026preserving)：只按内容做键时会碰撞，不兼容的 KV 让准确率降到 0。

  结论：**latent 论坛需要版本号和出处**。
- **跨模型家族**：普遍失败。[deng2026augment](#paper:deng2026augment)、[KV Provenance](#paper:song2026preserving) 是反例；[SwaT](#paper:alabdulkareem2026swarm) 是孤例，缺对照。所以 MVP 限定同权重模型。

### 2.4 共享空间的“结构”：五种范式（M3 检索的归纳）

| 范式 | 代表 | 已知弱点 |
|---|---|---|
| 工作区竞争 + 广播 | [Goyal 共享工作区](#paper:goyal2021coordination)、[CTM-AI](#paper:yu2026ctm)、[J-space](#paper:gurnee2026verbalizable) | 容量小；全广播，没有寻址 |
| 槽位 / 固定 latent 数组 | [CondenseFlow](#paper:chen2026condenseflow) 等 | 要训练；压缩会丢实体身份 |
| 内容寻址 | [MaSRead](#paper:baquero2026masread)、文本侧的 [ScaleMAS](#paper:qi2026scaling) | 基本只有单写者；冲突和过时没人处理 |
| KV 共享 / 并发注意力 | [Hogwild!](#paper:rodionov2025hogwild)、[LatentMAS](#paper:zou2025latent) | 无结构；读负担和干扰随规模增长 |
| 靠复制或筛选自发涌现 | [Copying in the Wild](#paper:marzo2026copying)、[Form Without Function](#paper:zerhoudi2026form) | 先写者定下约定；常常徒有其形 |

还有一条直接相关的理论：[MAS 信息瓶颈](#paper:yu2026multib)（NeurIPS 2026）认为，中继带宽无限时，多 agent 等价于单 agent 共享上下文；中继有损时，强模型获益反而少。**这给出了隐式论坛的上限，也给出了它为何可能有用的理由。**

## 3. 方法与测量（2026-10-18 精简版）

原则：一个简单、免训练的方法，加一个信息量已知的测量基准，用来揭示现象。不影响现象的机制一律拿掉。

### 3.1 方法：从上下文读出的潜在帖子

- **发帖.**
  1. 作者的上下文 C 包括它的任务、写的代码、CI 给的测试结果和它自己的汇报。
  2. 在 C 末尾接 k 个固定的查询向量（随机取的词表 embedding）。C 的 KV cache 直接复用，所以只跑 k 个位置的一次前向。
  3. 取这 k 个位置的末层状态，用 W_a 映射回输入 embedding 空间，去掉落在控制 token（`<|im_end|>`、`</think>` 等）方向上的分量，再缩放到平均 embedding 的范数，得到 k 个 soft token。

  不训练任何参数。
- **读帖.** 读者是同一个冻结模型。帖子作为 k 个 soft token 插进它的提示，前面加一行明文出处 `[post i] from agent1 on encode:`。读者自己的上下文保持不变，帖子只做增补。
- **论坛.** 帖子的集合。读者收到与自己任务相关的帖子；负载实验里，同时收到 M 条。
- **只有三个旋钮**：k；查询向量的来源（随机词表向量，或一段固定提示的 token）；取哪一层。

和已有方法的区别：

| 方法 | 传什么 | 要训练吗 | 和本方法的差别 |
|---|---|---|---|
| 隐状态池化（我们的旧版；Interlat 的免训练形式） | 作者所写那几句话的隐状态 | 否（Interlat 要） | 只读作者说出来的话，不读整个上下文 |
| [LatentMAS](#paper:zou2025latent) | 自回归生成的潜在思考，经 KV 工作记忆传递 | 否 | 本方法不自回归，k 个查询并行读出，只传 k 个向量 |
| [AC](#paper:ramesh2025communicating) | 中间层激活，与读者的激活合并 | 否 | 本方法作为输入 token 增补，不改写读者的计算 |
| [KVCOMM](#paper:ye2025kvcomm) / [KVComm](#paper:shi2025kvcomm) | 作者的（部分）KV cache | 否 | 本方法的大小与上下文长度无关，不需要位置校正 |
| [C2C](#paper:fu2025cache)、gist / ICAE | 融合后的 KV / 压缩 token | 是 | 本方法不训练压缩器 |

[LatentMAS 对齐矩阵的消融](#paper:deshpande2026role) 发现，代码任务上文本多 agent 优于 latent 通信；[deng2026close](#paper:deng2026close) 发现免训练地替换 KV 行不通，增补才有效。这与我们池化版的阴性结果一致（R2、R10），所以对比必须做在同一基准上。

### 3.2 测量基准

- **每个项目.** 生产者持有一项随机生成、无法猜出的私有约定：记录格式，包括标签、分隔符、字段顺序。标签长度可调，从而信息量可调。消费者必须从帖子得知这项约定，它写的代码由隐藏测试判定；消费者的 docstring 和可见测试都不泄露约定。
- **生产者的上下文可以合成**：参考实现加模板汇报，不必跑多 agent 循环，所以样本量不受限，条件也完全可控。
- **作者的话分三种.**
  - 如实：写出格式。
  - 省略：只说“按项目的记录格式”。
  - 说错：给出一个具体、听上去合理、但错误的格式。
- **每个条件三个数.**
  1. **传递率**：消费者代码通过隐藏测试的比例。
  2. **跟随所知 / 跟随所言**：作者说错时，读者代码用的是真格式还是作者说的假格式；作者省略时，读者是否仍拿到了格式（泄露率）。
  3. **用说差**：对同一条帖子，读者写进代码的（用）减去被直接问起时说出的（说）。
- **对照只有两个.**
  - 无帖子。
  - 换成另一个作者的帖子（移植）。移植时看读者是否写出了那个作者的格式；这同时是因果检验。

### 3.3 精简：砍掉什么、保留什么

| 组件 | 原设计 | 现在 | 理由 |
|---|---|---|---|
| 多 agent 调度：自选任务、轮次、认领、重试、依赖优先 / 等待 | 主管线 | 降为最后的端到端演示 | 现象不需要它；它还制造了混淆，如 R10 的时序误判、作者忘了自己定的格式（R11） |
| 零信任机制：attested / crosscheck / STALE / 版本号 / 信誉 | 4 种信任模式 | 保留“核对说法”本身，作为比较对象：不核对 / 重新执行（attested）/ 同伴测试（crosscheck）/ 潜在信号；STALE、版本号、信誉不进主线 | 2026-10-18 更正：零信任指“看到说法后主动核对”，不是不传话。核对方式的准确率与代价本身就是现象（R1：执行只覆盖测试写到的部分；R9：同伴测试 77% 是错的） |
| 伪说辞的 4 种模式，加 1-bit DONE 标记 | always / pressure / deceive / mislead | 合并为作者话语的三种：如实 / 省略 / 说错 | 内容层面的谎言才有意思；DONE 标记是软工概念 |
| ClassEval 拆分任务 | 主基准 | 移出主线 | 不交流也能做（R2、R6）；只保留“免训练 latent 干扰读者”这一条 |
| 分块平均 writer | 免训练 latent | 换成从上下文读出；映射回输入空间的三步（W_a、去掉控制 token 方向、按平均 embedding 范数缩放）保留 | 原以为分块平均是抹掉内容的原因；R13 更正后，从上下文读出的版本同样传不过内容，两者都留作对照 |
| 读取侧 adapter（E1a）、多目标 writer 训练（E1w）、合成数据训练（E1s） | 三条训练线 | 方法不训练；训练只作一个消融 | 未训练的版本已经最好，训练反而抹掉内容；三条训练线是工程量的主要来源 |
| 询问：三问 + 线性探针 + 中性上下文探针 + 隐藏测试探针 | 四套 | 两个数：读者说出的 vs 读者用出的；线性探针只作“信息在不在”的上界 | 说用分离本身就是现象 |
| 指标：method_pass、class_pass、false_declaration、propagation 等十几个 | 软工指标 | 三个：传递率；跟随所知 vs 所言；用说差 | |
| 结构谱 L0–L3；对照 zero / mean / noise | 实验变量 | 只留“有 / 无出处标题”一个开关；对照只留无帖子与移植 | |
| 长程 SWE 测试床：Commit0、Apptainer、git diff 失效、8–32 agent | 下一阶段 | 换成“一个读者面对 M 条帖子”的负载曲线；真实长程项目只做小规模演示 | “一大群”的本质是许多潜在帖子同时在场时会不会互相干扰、能否按出处找到，这不需要搭仓库 |
| 群体进化 | 下一阶段 | 留作延伸 | |

保留的几样：
- 同一个冻结模型，方法零训练。
- 用代码执行判对错：客观，这也是代码场景真正的价值。
- 出处是一行明文：便宜，并且让论坛可寻址。
- 受信推理的前提。
- 移植对照。

### 3.4 实验清单

1. **主表**：信道 × 三种作者话语，各报三个数。信道包括：
   - 无帖子、文本、贴代码；
   - 共享作者的完整上下文（上界）；
   - 隐状态池化、LatentMAS 式潜在思考、AC 式激活合并；
   - 本方法，以及本方法 + 训练（消融）。

   共享完整上下文同样会跟随所知，代价是长度和全部隐私；本方法只用 k 个向量。
2. **容量曲线**：标签长度（信息量）× k。
3. **论坛负载**：同时在场的帖子数 M = 1, 2, 4, 8, 16，有 / 无出处标题。
4. **因果分析**：
   - 移植；
   - 只改作者上下文里的格式，保持作者的话不变；
   - 按层、按查询位置做消融。
5. **第二个模型**：本地已有 Qwen3.5-9B，它是混合线性注意力，架构与 Qwen3-8B 不同。如需跨家族，再加一个非 Qwen 的开源模型。
6. **端到端演示**：放回多 agent 论坛。E0s3、E0s4 已排队。
7. **核对方式（待确认，2026-10-18）**：按“看到说法后主动核对”的零信任定义，帖子保留作者的文字，同时附上从作者上下文读出的潜在信号作为核对证据。比较四种核对方式的准确率与代价：不核对 / 重新执行 / 同伴测试 / 潜在信号。再测一个现象：文字和潜在信号矛盾时，读者跟哪一边。

## 4. 已做的实验与结果

> **更正（2026-10-18）：解码方式。** 代码要求贪心解码，但 transformers ≥ 4.50 会把等于其全局默认值的生成参数（`do_sample=False`、`temperature=1` 等）悄悄换成模型自带的值。所以下面所有结果（R1–R13，以及当天的 E1s2、E0s3、E0s4 和离线测量）实际都是**按 Qwen3 的默认参数采样**：temperature 0.6、top-p 0.95、top-k 20。没有显式设随机种子，用的是 PyTorch 的默认种子，所以同一配置重跑大体相同（R1 里 30 个项目有 25 个完全一致），剩下的差异来自 GPU 数值的非确定性。
>
> 各条件之间的比较仍然公平，因为解码方式相同；但单个种子的结果里含有采样噪声，需要多种子复核。现在代码显式写明这组采样参数，并关掉了自动替换（`use_model_defaults=False`），运行的就是写出来的配置；`--temperature 0` 才是真正的贪心。

### smoke 观察（2026-10-17，作业 24329408）

只跑了 3 个项目，每个 3 个 agent，1/3 的 agent 被注入虚报。样本太小，只能看方向，不能下结论。

- **免训练 latent 基本问不出内容。**
  - text 帖子：问“关于哪个方法”准确率 1.00，用别人帖子回答的基线 0.00；问“代码是否通过”约 0.93，基线 0.56–0.76。
  - latent 帖子：问“关于哪个方法”0.38–0.41，基线 0.24–0.30，多出的部分主要来自读者倾向于选第一个选项；问“代码是否通过”与基线持平。
  - 这与 H3 的预期一致。
- **注入的 latent 会让读者生成崩溃。** 部分 report 退化成“</think> Okay Okay …”。原因推断：最后一个 token 的末层状态预测的是回合结束，经 W_a 映射后落在 `<|im_end|>`、`</think>` 等控制 token 的 embedding 附近，打乱了 chat 结构。
  - 已修正：丢弃最后一个位置，并把 latent 投影到控制 token embedding 张成空间的正交补上。
  - 另加 `degenerate` 计数，作为“latent 信道干扰接收方”的风险指标。
  - 这一现象本身值得写进论文：**未经训练的隐式信道，可能无意中对接收方构成攻击**。
- **attested 确实能压住群体虚报：** 团队宣布完成、但隐藏测试不过的比例（`false_declaration`），blind 下为 0.67，attested 下为 0–0.33。剩下没压住的，都是“可见测试过、隐藏测试不过”的情况，CI 本来就看不到。
- **方法学修正：**
  - 依赖方法写坏时，调用方会在测试中机械地失败，这会混进传播指标。现在加了**隔离评测**，把其他方法换成参考实现后，只测本方法；传播指标改用隔离结果。
  - LLM 选题时常常先挑有依赖的方法，导致“读依赖帖子”的情形几乎不出现。改为默认依赖优先（`deps_first`）。

### E0 与 E1a 结果（2026-10-17，作业 24332670、24336678）

设置：30 个 ClassEval 项目，3 个 agent，Qwen3-8B，单 seed。解码当时以为是 greedy，实际是 Qwen3 的默认采样（temperature 0.6、top-p 0.95、top-k 20），见 §4 开头的更正。区间是对项目做 bootstrap 或 Wilson 的 95% CI。完整表格见 `doc/results/E0_table.md` 和 `doc/results/E0_claims_probes.md`。

**R1　零信任闸门有效，但只对“明知虚报”有效。**

| 条件（text 信道） | false_declaration | 明知虚报率 |
|---|---|---|
| 1/3 注入虚报，blind | 0.60 [0.43, 0.77] | 0.14（含注入） |
| 1/3 注入虚报，attested | **0.33** [0.17, 0.50] | 0.27（含注入） |
| 全员诚实，blind | 0.33 [0.17, 0.50] | **0.027**（3/112） |
| 全员诚实，attested | 0.37 [0.20, 0.53] | 0.051 |
| 1/3 受完成压力，blind | 0.37 [0.20, 0.53] | 0.054 |

- 注入的虚报把团队的虚假完成宣告从 0.33 推到 0.60，attested 能把它压回 0.33。
- 但在**自然条件**下，虚假宣告主要来自“可见测试过、隐藏测试不过”：作者自己的代码有错却报 DONE 的比例是 15–18%，CI 看不到这类错误，所以 attested 无效。
- Qwen3-8B 自发的明知虚报很少，只有 2.7%；完成压力提示只把它推到 5.4%。
- 这支持把叙事定为“**能力驱动的虚报**”，也说明零信任需要比可见测试更强的验证者。
- **运行间噪声**：同一配置（全员诚实、text、blind）意外重跑了一次（作业 24345097），30 个项目里 25 个结果完全相同，其余由 GPU 数值的非确定性造成翻转。`method_pass` 为 0.776 vs 0.769，`false_declaration` 为 0.33 vs 0.40。所以 30 个项目上约 0.07 的差别属于噪声范围；0.60 vs 0.33 远超这个量级。

**R2　免训练的 latent 论坛在功能上等于“不通信”。**

| 条件（blind） | method_pass | 问 CI（自身 / 换别人帖子） |
|---|---|---|
| none | 0.73 | – |
| text | 0.76 | 0.98 / 0.71 |
| latent | 0.74 | 0.37 / 0.39 |
| latent + shuffle | 0.74 | 0.33 / 0.34 |
| latent + zero | 0.73 | 0.44 / 0.43 |
| artifact-latent | 0.74 | 0.38 / 0.38 |

- 三种对照下完成度不变，冻结读者从 latent 里问不出任何东西。这与 H3 和 deng2026close 一致。
- 在这个规模的任务上，连 text 也只比 none 高约 3 个点，所以 ClassEval 对“交流是否有用”的区分度很低。这是转向 E2 长程任务的又一个理由。

**R3　信息在 latent 里，读不出来是读者的问题。** 线性探针，按项目分组 5 折交叉验证：

| latent 来源 | verified | verified∣claimed | 标签置换基线 |
|---|---|---|---|
| report-latent（作者的消息，可能已被篡改为 DONE） | 0.97–0.997 | **0.92–0.99** | ≈ 0.5 |
| artifact-latent（受信 harness 编码代码和 CI 日志） | 0.90–0.95 | 0.93–0.96 | ≈ 0.5 |

即使只看声称 DONE 的帖子，作者消息的 latent 也能把真 PASS 和假 DONE 分开。不过作者写消息时，上下文里就有可见测试的结果，所以要排除“探针只是在读消息文本里的失败字样”这种解释。

**中性上下文对照**（`neutral_probe.py`，作业 24339519；E0 task1 的 1341 条帖子，其中 156 条被篡改）。同一段消息文本，不带项目、代码、测试日志重新编码一次，再用同样的探针：

| 目标 | 作者上下文（writer） | 只有文本（neutral） |
|---|---|---|
| verified | 0.990 | 0.957 |
| verified∣claimed | **0.965** | 0.872 |
| 被篡改 vs 诚实的 DONE | **0.989** | 0.919 |
| claim | 0.957 | **0.984** |

- 大部分信号其实就在文本里：E0 的篡改只改 STATUS 一行，正文往往还在描述失败，所以只看文本也能以 0.92 识别篡改。
- 作者上下文的 latent 多带了一部分真实状态：在声称 DONE 的帖子里，探针的剩余误差（1 − AUROC）从 0.128 降到 0.035，约减少 73%。
- 方向值得注意：writer latent 对“真实状态”更准，对“声称了什么”反而更差（0.957 vs 0.984）。在作者上下文里计算的 latent，偏向上下文里的事实，而不是消息里的说法。
- 局限：这里的谎言很粗糙。更严格的检验是让 agent 自己写一段连贯、不留痕迹的谎言（`overclaim_mode=deceive`，E0d，作业 24427700）。

**CI 看不到的 bug**（CPU 作业 24428190/1；各条件的帖子合并，按项目分组交叉验证）。只看可见测试已通过的帖子，预测隔离隐藏测试的结果：

| latent 来源 | n（其中隐藏测试不过） | AUROC | 置换基线 |
|---|---|---|---|
| report-latent（作者上下文） | 635（85） | **0.65** | 0.47 |
| artifact-latent（代码 + CI 日志） | 425（54） | 0.54 | 0.49 |

- 作者上下文的 latent 带有一个弱但高于随机的“自我怀疑”信号，粗略 95% 区间约为 [0.55, 0.75]。只编码代码本身的 artifact-latent 几乎没有。
- 按单个条件算时，每组只有约 14 个负例，AUROC 在 0.43–0.74 之间乱跳。这个目标必须合并样本才能看。
- 含义：单靠探针，替代不了更强的验证者（同伴测试 E0c 或隐藏测试）。它更适合做排序信号，把审查预算优先分给可疑的帖子。

**R4　只训练读取侧，就能问出粗粒度状态，问不出实例身份。** E1a 用 artifact-latent，冻结 Qwen3-8B，只训练一个秩 64 的残差 adapter，跑 1500 步。测试集是 7 个留出项目、176 条帖子：

| 问题 | 训练前（自身 / 换别人） | 训练后（自身 / 换别人） | 基线 |
|---|---|---|---|
| 是否过 CI | 0.45 / 0.45 | **0.94** / 0.48 | 多数类 0.55 |
| 是否声称 DONE | 0.36 / 0.34 | **0.81** / 0.53 | 多数类 0.68 |
| 关于哪个方法 | 0.27 / 0.28 | 0.35 / 0.27 | 随机 0.25 |
| 虚报帖里问出 FAIL（n=23） | – | **0.74** / 0.39 | – |
| 复述 loss | 4.29 / 4.31 | 1.76 / 1.81 | – |

latent 经过训练的读取侧之后，可以像 breakpoint 一样被“问出来”，但只限于 1-bit 级别的全局状态。方法身份几乎问不出，复述能力的提升也主要是通用的。这与“latent 传的是模式或状态、不是实例内容”的猜想吻合。分块平均压缩，很可能抹掉了实体身份（XBridge 也报告过这一点）。**不分块的版本（k=128，E0k，作业 24436973_1）**：对免训练读者毫无帮助，反而更有害。
- 论坛结果不变：`method_pass_iso` 0.76，与 k=16 相同。
- 收到 latent 的调用里，生成崩溃的比例升到 43% / 30%（attested / blind）；k=16 时是 19% / 12%。
- 冻结读者的三问甚至低于“换别人帖子”的基线：问 CI 0.32 vs 0.46。
- 线性探针几乎不变：verified 0.96，verified∣claimed 0.87–0.93。

所以，“多给向量”不能替代训练。

**在 k=128 上训练读取侧**（E1a，作业 24440472；488 条帖子，按项目划分，7 个留出项目，评测 118 条）：

| 问题 | 训练后（自身 / 换别人） | k=16 的 report-latent E1a | 基线 |
|---|---|---|---|
| 是否过 CI | **0.88** / 0.48 | 0.82 / 0.45 | 多数类 0.63 |
| 是否声称 DONE | 0.82 / 0.53 | 0.735 / 0.475 | 多数类 0.53 |
| 关于哪个方法 | 0.415 / 0.407 | 0.305 / 0.31 | 随机 0.26 |
| 虚报帖里问出 FAIL（n=19） | **0.95** / 0.42 | 0.64 / 0.68 | – |
| 复述 loss | **1.50** / 2.12 | 1.80 / 1.99 | – |

- 不分块之后，训练过的读者**能在虚报帖上问出真相**（18/19，对照 8/19）；k=16 时完全做不到。复述也明显更依赖自己的 latent。
- 所以 R4 里“读不到真相”的原因，主要是分块平均把信息压掉了，而不是读者读不了。
- “关于哪个方法”仍然问不出来：自身与对照同步上升，是先验，不是内容。实例身份问题还在，这正是 SecretBench 和 E1w 要回答的。
- 样本小（7 个项目、19 条虚报），需要更大的 k=128 数据来复核。

**report-latent 版本的 E1a**（作业 24339523）：1341 条帖子，按项目划分为训练 1020 / 测试 321（7 个留出项目），评测 200 条。

| 问题 | 训练前（自身 / 换别人） | 训练后（自身 / 换别人） | 基线 |
|---|---|---|---|
| 是否过 CI | 0.52 / 0.53 | **0.82** / 0.45 | 多数类 0.555 |
| 是否声称 DONE | 0.41 / 0.42 | **0.735** / 0.475 | 多数类 0.585 |
| 关于哪个方法 | 0.26 / 0.245 | 0.305 / 0.31 | 随机 0.25 |
| 虚报帖里问出 FAIL（n=28） | 0.93 / 0.93* | 0.64 / 0.68 | – |
| 复述 loss | 3.76 / 3.78 | 1.80 / 1.99 | – |

\*训练前的读者几乎总答 FAIL，所以这个数没有意义。

- 能问出粗粒度状态，但比 artifact-latent 弱（0.82 vs 0.94），更远低于线性探针（0.99）。
- **关键阴性结果**：在被篡改的帖子上，训练后的读者并不比“拿别人的 latent 回答”更会说 FAIL（0.64 vs 0.68）。线性探针能找到的“真实状态”方向，冻结 LLM 加一个小 adapter、1020 条样本，并没有学会去读；它学到的更像是总体的 PASS/FAIL 统计和声称的内容。
- 含义：**线性可解码 ≠ 接收方能读到**。可问性要么需要显式的对比目标（在篡改帖上加权），要么把“读真相”交给一个独立于 agent 的可信探针。探针结果只进日志，不回流给 agent，否则 agent 会学着骗过探针（Feedback Evasion）。

**R5　风险：未经训练的 latent 会干扰接收方。** 带 report-latent 的调用里，有 12–19% 的生成崩溃，例如 blind 下 21/175。全零 latent 是 0/183；artifact-latent 不到 2%。所以免训练的隐式信道不只是没有用，还会实际损害接收方。

### 2026-10-18 结果：私有规格、连贯谎言

**R6　在 ClassEval 上，即使藏起 docstring，文本交流也没有用。**（E0p，作业 24428033；70 个项目，86 个依赖方法，隔离隐藏测试；配对比较用精确符号检验）

| 条件 | 依赖方法 | 其余方法 | class_pass |
|---|---|---|---|
| full 规格，不通信（上界） | 0.709 | 0.829 | 0.41 |
| private，不通信 | 0.616 | 0.770 | 0.24 |
| private，text | 0.616 | 0.788 | 0.30 |
| private，免训练 latent | 0.570 | – | 0.24（136 次生成崩溃） |

- private vs full，依赖方法上不一致的计数是 5 / 13，p = 0.10；text vs private-none 是 7 / 7。也就是说，文本帖子没有把 full 规格的优势补回来。
- 读者确实读到了依赖方法的帖子（222 次依赖方法尝试里有 191 次），帖子本身也像样，例如“检查 URI 是否以 /api 或 /login 开头，返回 bool”。
- 失败的依赖方法里，多数和接口无关，而是可见测试通过、隐藏测试不过，或者没写出合法定义。ClassEval 的接口大多可以从方法名和调用方自己的 docstring 推出来。
- 结论：ClassEval 不是一个“必须交流”的基准。要测量信道到底传了多少实例内容，需要**无法猜出的信息**。为此做了 SecretBench（下一段）。

**SecretBench（`benchmark/secretbench.py`）。** 每个项目有一个生产者 `encode`，按私有格式写记录：随机 4 字母标签、分隔符、与签名不同的字段顺序，约 23 bit。另有三个消费者 `decode` / `is_record` / `get_field`，各需要格式的不同部分。消费者的 docstring 和可见测试都不泄露格式，所以 CI 也给不出提示；朴素猜测能过可见测试，过不了隐藏测试。在 private 规格下，消费者只能从论坛得知格式，或者在运行时调用 `encode` 反推（这是合法的“经由代码”的信道，单独统计）。full 规格是上界。E0s（作业 24442380）在 40 个项目上跑 private × none / text / latent 与 full × none。

**R7　连贯的谎言在文本里不留痕迹，但团队层面的后果和粗糙篡改差不多。**（E0d task1/2，70 个项目，text 信道）

| 条件 | false_declaration | 询问虚报帖：问出 FAIL | 基线（换别人帖子） |
|---|---|---|---|
| 粗糙篡改，blind | 0.57 | 0.79 | 0.54 |
| 粗糙篡改，attested | 0.40 | 0.73 | 0.43 |
| 连贯谎言，blind | 0.59 | **0.04** | 0.38 |
| 连贯谎言，attested | 0.33 | **0.06** | 0.40 |

- 让 agent 自己写谎言之后，从文本里几乎问不出 FAIL，甚至低于“换别人帖子”的基线，100% 复述 DONE。也就是说，对文本做 breakpoint 询问，对连贯谎言无效。
- 团队宣布完成却不过的比例，两种谎言差不多，attested 都能压下来。队友在 full 规格下自己有 docstring，所以状态谎言很少传导成代码错误：读到依赖方法虚假 DONE 的尝试，通过率并不更低（0.51 vs 0.42，blind）。

**R8　连贯的谎言骗得过文本，骗不过作者上下文里的 latent。**（E0d task0，latent 信道，70 个项目 × blind / attested，1142 条帖子，其中 152 条是谎言；线性探针，按项目分组交叉验证）

| 目标 | 作者上下文（writer） | 只有文本（neutral） |
|---|---|---|
| 说谎者的 DONE 帖：谎言 vs 真 DONE（n=338，45% 是谎言） | **0.91** | 0.71 |
| 所有 DONE 帖：谎言 vs 诚实 | **0.93** | 0.78 |
| verified∣claimed | **0.95** | 0.80 |
| claim | 0.96 | 0.98 |
| CI 看不到的 bug（hidden∣visible_pass，n=552） | 0.53 | 0.53 |

- 这是 H4 最干净的一次检验。说谎者每次汇报都收到同一条“声称 DONE”的指令，所以诚实帖和谎言帖之间只差测试结果。文本是模型自己写的谎言，冻结读者对文本提问，几乎问不出 FAIL（R7）。
- 但是 latent 在作者的上下文里计算，仍把谎言和真话分得很开：剩余误差从 0.29 降到 0.09。文本本身也留了一点痕迹（0.71），只是少得多。
- **CI 看不到的 bug，这次没有复现**（0.53 vs 上次 0.65）。这个信号目前不稳健，不能作为结论。
- 合起来的结论：**在受信推理的前提下，latent 帖子比文本更难撒谎**。这个“难”是对一个训练过的审计者（探针）而言的，接收方的冻结模型并读不到它（R4）。

**R9　同伴验证本身不可信：同伴写的测试 77% 是错的。**（E0c，作业 24436973_0；30 个项目，text 信道，完成压力）

| 条件 | method_pass | class_pass | declared_done | false_declaration | prompt tokens |
|---|---|---|---|---|---|
| 诚实，attested | 0.745 | 0.43 | 0.67 | 0.23 | 0.66M |
| 诚实，crosscheck | 0.69 | 0.30 | 0.50 | 0.20 | 1.73M |
| 1/3 受压，attested | 0.776 | 0.43 | 0.80 | 0.37 | 0.60M |
| 1/3 受压，crosscheck | 0.67 | 0.37 | 0.57 | 0.20 | 1.68M |

- crosscheck 下共做了 844 次同伴检验，其中 700 次判为 FAIL。可是同伴测试在参考实现上就不过的占 631 次（**77%**）。真正抓到 bug 的只有 12 次，FAIL 判定的精度不到 2%。
- false_declaration 下降，不是因为抓到了 bug，而是错误的同伴测试堵住了子任务的关闭：宣布完成的比例从 0.67–0.80 降到 0.50–0.57，`method_pass` 降了 6–11 个点，token 成本是 2.6 倍。
- 含义：在零信任的群体里，**验证者也是一个不可信的信道**。由 8B 模型只凭 docstring 写的测试，比被检验的代码更不可靠。可行的改进方向有三个：同伴测试先要通过多个独立实现的投票（N-version）；作者可以对测试提出异议并由第三方裁决；或者只信受信的隐藏测试。这一条也支持“验证者可靠性”应当进入论坛设计的核心。
- 另外，attested 下受压 agent 的明知虚报占 DONE 帖的 14%（都被可见测试拦住）；E0 里 blind 下受压是 5.4%。差别可能来自 attested 会反复重开子任务，给了更多“硬报 DONE”的机会。

**R10　SecretBench：文本只传过去了一半，免训练 latent 什么都没传过去。**（E0s，作业 24442380；40 个项目，120 个消费者方法，隔离隐藏测试）

| 条件 | 消费者通过率 | decode / is_record / get_field | false_declaration |
|---|---|---|---|
| full 规格，不通信（上界） | **0.84** | 0.97 / 0.80 / 0.75 | 0.30 |
| private，不通信 | **0.00** | 0 / 0 / 0 | 0.13 |
| private，text | **0.43** | 0.42 / 0.42 / 0.45 | **0.93** |
| private，免训练 latent | **0.008** | 0 / 0 / 0.03 | 0.48 |

- 基准按设计工作：没有通信时消费者全错，也没有任何 agent 在运行时调用 `encode` 反推格式。这里的信道容量是可测的。
- 免训练 latent 等于没有信道，冻结读者问“关于哪个方法”只有 0.11。
- 文本只拿回了一半。最初的解释是“时序”加“读取”两种损失；复查后（R11）时序这一条不成立：那 25% 是测量框架的问题。真正的损失在读取。

**R11　更正：SecretBench 上文本的损失在“读取”，不在时序。**（E0s 复查 + E0s2，作业 24448455，三次 text 运行）

- **生产者总是先发帖。** 三次 text 运行里，没有一次消费者尝试开始于 `encode` 发帖之前：回合内 agent 依次行动，依赖优先总把 `encode` 先给第一个 agent。`deps_wait` 因此一次都没有触发（0 次等待），它对比默认的 `dep_pass_iso`（0.41 vs 0.35）在三次运行的噪声之内。
- **R10 说的 70 次“没读到生产者帖子”，全是 `encode` 的作者自己后来去写 `get_field`。** 论坛不给作者看自己的帖子，而测量框架也没给 agent 留下它先前写过的代码，所以它忘了自己定的格式。这 70 次全部失败。这是框架的缺陷，不是通信的损失。已加 `memory` 选项：agent 能看到自己先前为依赖写的代码（E0s3 起开启）。
- **只算“生产者是另一个 agent”的消费者**（n=112/次），text 的通过率是 0.46 / 0.38 / 0.44，full 规格是 0.85，不通信是 0。这才是信道本身的表现。
- **错在哪里**（两次 E0s2 运行里，生产者是别人的 80 个 decode）：失败 46 个，其中 36 个代码里标签写对了。最常见的错误是数错字段数（如 `len(parts) != 5`，25/46）和字段位置对错（16/46）。生产者的帖子 40/40 写了标签和全部字段名，但常是示意式的，有时自相矛盾，例如“'JJGF!year!author!title' structure … ensure inputs are in the correct order (title, author, year)”。
- **只在 ClassEval 上训练过的 writer head（E1w fold 0）也带不出秘密**：消费者通过率 0.008（1/120），和免训练 latent 一样；但 508 次带 latent 的生成里没有一次退化（免训练 latent 在 ClassEval 上是 15–20%）。它学到的是状态，不是内容（见 R12）。
- 帖子的写法决定了能不能用（三次运行，读过别人 `encode` 帖子的全部消费者尝试，含重试）：帖子里有 `'JJGF!year!author!title'` 这样的示意串时，成功率 0.31（n=329）；只有文字描述（“标签 X，后面依次是 qty、order_id、item，用 '!' 分隔”）时是 0.15（n=278）。没有一个生产者给出带真实值的样例记录。
- 含义：文本把信息带过去了，但自然语言转述对 8B 读者来说是不精确的接口规格；同一格式写进读者自己的 docstring 时，decode 通过率是 0.97。瓶颈在精度，不在带宽。E0s3 加了“直接贴代码”的文本基线（`source=artifact`），检验共享工件能否补上这一缺口。

**R12　训练 writer、读者不动：latent 帖子能被原版读者读懂“状态”，不再让读者崩，但带不出内容。**（E1w，作业 24437567 / 24437569 / 24444212；论坛 24437568 / 24437570）

writer head 在 E0p（私有规格）和 E0d（连贯谎言）的 latent 帖子上训练（约 1,000 条，按项目二折交叉拟合），读者是原版 Qwen3-8B、不加 adapter。评测在留出项目的 200 条帖子上；“self / other”是用帖子自己的 latent / 换成别的帖子的 latent 回答同一组问题：

| writer head | verified（多数类 0.515） | claim（0.62） | anchor（随机 0.23） | 虚报帖问出 FAIL（n=31） | recon loss |
|---|---|---|---|---|---|
| k=16，fold 0 | 0.865 / 0.54 | 0.83 / 0.515 | 0.325 / 0.275 | 0.84 / 0.58 | 1.46 / 1.63 |
| k=16，fold 1 | 0.93 / 0.51 | 0.765 / 0.52 | 0.335 / 0.295 | 0.68 / 0.55 | 1.70 / 1.90 |
| k=64，fold 0（3,000 步） | **0.96** / 0.485 | **0.94** / 0.555 | 0.345 / 0.275 | **0.94** / 0.48 | 1.44 / 1.63 |

- 原版读者从 latent 里读出了 CI 结果，在文字说 DONE、代码却没过的帖子上也是（k=64：0.94 vs 换帖 0.48）。E1a 只训读者时这一项是 0.64 / 0.68，等于没读出来。所以 R4 里的瓶颈确实在 writer 的分块平均。
- 要说清机制：可见测试的结果就在作者的上下文里（汇报 prompt 里写着），受信 writer 读的是整个上下文，又以 CI 结果为训练目标，所以它把作者“知道的”传了出去，而不是作者“说的”。这正是 R8 的“latent 更难说谎”，但这次不需要探针，原版读者自己就能读出。反面是隐私风险：作者没写进消息的东西，latent 也会带出去。
- 实例内容几乎没有带出来：“关于哪个方法”只有 0.33–0.35（换帖 0.28–0.30），k 从 16 加到 64 也没变。
- 接回私有规格的 ClassEval 论坛（每折 35 个它没见过的项目），和 E0p 同一批项目比：

| 同批留出项目 | fold 0：method_iso / dep_iso / 虚假完成 | fold 1 | 带 latent 的生成中退化的比例 |
|---|---|---|---|
| full，不通信 | 0.836 / 0.675 / 0.26 | 0.756 / 0.739 / 0.37 | — |

| private，text | 0.796 / 0.600 / 0.43 | 0.686 / 0.630 / 0.49 | — |
| private，免训练 latent | 0.796 / 0.600 / 0.40 | 0.647 / 0.543 / 0.49 | 46/298、90/456（15–20%） |
| private，writer head | 0.803 / 0.575 / 0.34 | 0.667 / 0.565 / 0.43 | **0/373、0/490** |

- 任务上和不通信没有差别，shuffle 也一样（两折 writer head vs shuffle：1/3、4/7 个方法不一致，p = 0.63、0.55）：ClassEval 上本来就没有必须传的内容（R6）。可测的收益只有一条：**训练过的 writer 让 latent 不再把读者带崩**，免训练 latent 有 15–20% 的生成退化，writer head 是 0。
- 这个 head 在 SecretBench 上也带不出秘密（R11，0.008）。下一步 E1s：直接在“必须传的内容”上训练 writer。

**R13（已更正，2026-10-18）　未训练的 gist writer 并没有把秘密交给读者；原来的正面结果来自评测代码的 bug。**（E1s，作业 24455828；复核：E1s2 作业 24505239、离线测量 24509236、论坛 E0s4 作业 24505241）

原先的结论是：未训练 head 的 latent 让冻结读者写出的 decode 有 0.45 通过（文字 0.35），而且读者"用得出、说不出"。**这两条都撤回。**

原因在评测代码 `train_secret.evaluate`：它只在臂名恰好是 `self` 或 `other` 时才把 latent 交给读者。未训练 head 那一臂叫 `self_step0`，于是：
- 读者没有收到 latent；
- 写代码的提示里出现的是帖子原文，因为 `forum_block` 把不认识的类型当成了文字；
- 被直接提问时，读者收到的是"(no message)"。

所以"0.45 超过文字"其实是文字对文字（两臂的 decode 结果在 40 个项目里有 36 个一致，差别是采样噪声），"问不出来"只是因为提问时确实什么都没给。这个臂的回答分布和"无帖子"臂完全一样，大多是"The message is empty"。

把 latent 正确交给读者之后，三次独立复核的结论一致：未训练的 gist latent 和分块平均一样，几乎什么也没带过去。

| 复核 | 读者收到的 | decode / 消费者通过率 | 代码里写出真标签 |
|---|---|---|---|
| E1s2（旧代码，40 条真实生产者帖子） | 未训练 head 的 latent | decode 0.05，合计 0.017 | — |
| E1s2 | 换成别的帖子的 latent | 0 | — |
| 离线测量（40 个合成项目，如实汇报） | 本方法（random:16） | 合计 0.025 | 0.0 |
| 离线测量 | 分块平均（chunk:16） | 0 | 0.0 |
| 离线测量 | 文字 | 合计 0.66 | 0.85 |
| 论坛 E0s4（破坏者，生产者是别的 agent） | 本方法 / 文字 | 0.010 / 0.307 | — |

仍然成立的部分：
- 在合成数据上训练这个 head 会把输出收成模板：读者写出格式规整、标签却错的记录（如 `'PZQX~1965~Herbert~Dune'`），这一臂正确地拿到了 latent。E1s2 的只训 query、低学习率两种变体也没有改善：每 150 步在 20 条真实帖子上追踪，decode 在第 150 步短暂升到 0.15（只训 query）和 0.25（低学习率，20 条中 5 条），到第 300 步都回到 0，训练结束时 self 和 other 都是 0。低学习率那一臂的损失从 2.7 降到 0.5，说明它学会的是合成数据里的模板，而不是从上下文读出实例。
- 未训练的 gist latent 不会把读者带崩（E0s4：282 次带 latent 的生成，0 次退化）。

这个 bug 是我写的，而我把它的结果当成了主要的正面证据。`training/secret.py` 已修正：只要传入 latent 就交给读者，`forum_block` 遇到未知类型直接报错，并补了回归测试。

**R14　离线 SecretBench 测量：作者说什么，读者就照着写；附上潜在帖子也不改变这一点。**（作业 24509236，任务 0–2；每格 40 个合成项目；解码为 Qwen3 默认采样）

| 作者的话 | 信道 | 消费者通过率 | 代码里是真标签 | 代码里是作者说的假标签 | 直接问时答出真标签 |
|---|---|---|---|---|---|
| — | 不交流 | 0 | 0 | — | 0 |
| 如实 | 文字 | 0.66 | 0.85 | — | 1.0 |
| 如实 | 文字 + 本方法 | 0.70 | 0.86 | — | 1.0 |
| 如实 | 文字 + 分块平均 | 0.54 | 0.93 | — | 1.0 |
| 如实 | 本方法 / 分块平均（只给 latent） | 0.025 / 0 | 0 / 0 | — | 0 / 0 |
| 省略 | 文字 / 本方法 / 两者 | ≈ 0 | 0 | — | 0 |
| 说错 | 文字 | 0 | 0 | **0.85** | 0 |
| 说错 | 文字 + 本方法 / 文字 + 分块平均 | 0 | 0 | **0.84 / 0.93** | 0 |
| 说错 | 只给 latent | ≈ 0 | 0 | 0 | 0 |

- 文字照常起作用，读者也照常被文字骗：作者把格式说错时，85% 的读者代码直接用了假标签。
- 附上从作者上下文读出的 latent，对读者几乎没有影响：如实时略有升降（0.70 / 0.54 对 0.66，在噪声范围内），说错时仍然 84–93% 跟着假格式走。冻结的读者读不出 latent 里的内容，也就谈不上用它来核对说法。
- 移植对照（把别的项目的 latent 给读者）：读者代码里从没出现那个项目的标签（0/40），与"latent 里没有可用内容"一致。

| 标签字母数 | 信息量（bit） | 文字：通过率 | 文字：代码里是真标签 | 文字：直接问时答出 | 本方法：通过率 | 移植对照 |
|---|---|---|---|---|---|---|
| 2 | 14.3 | 0.54 | 0.85 | 1.0 | 0.013 | 0.025 |
| 4 | 23.7 | 0.66 | 0.85 | 1.0 | 0.025 | — |
| 8 | 42.5 | 0.53 | 0.78 | 1.0 | 0.038 | 0.025 |

（4 字母那一行来自任务 0。每格 40 个项目、80 段消费者代码，通过率的标准误约 0.05。）

- 本方法在所有信息量下都和移植对照一样，贴着地板，所以画不出容量曲线：不是容量不够，而是冻结读者根本没从里面读到内容。
- 文字信道有一个小而一致的现象：读者被直接问时 100% 能复述标签，写代码时却只有 73–85% 用上了它，信息越多，用上的越少。也就是说，对文字消息，"问得出"高估了"用得上"。这和已撤回的"用得出、说不出"方向正好相反。

**这对故事意味着什么。** 至今没有任何一种 latent 信道能把实例内容交给一个冻结的读者：免训练的两种写法都不行；训练过的 writer 只学会了状态，在 SecretBench 上学成了模板。站得住的正面证据只剩两条，而且都在"状态"层面：
- 作者上下文里算出的 latent，经线性探针可以区分谎言和真话（R3、R8）；
- 训练过的 writer 让原版读者能读出真实的测试结果，即使作者说了谎（R12）。

这正好对应"零信任 = 看到说法后主动核对"：latent 不必代替文字去传内容，而是作为核对"做完了吗、测试过了吗"这类说法的证据。下一步应当围绕这一点设计。

**R15　论坛里作者诚实时：贴原始产物 > 作者自述 ≫ 潜在帖子 ≈ 不交流。**（E0s3，作业 24505240；40 个 SecretBench 项目，私有规格，agent 带记忆；只统计生产者是别的 agent 的消费者）

| 帖子 | 跨 agent 的消费者通过率 | 依赖方法隔离通过率 | 整个类通过 | 宣布完成但隐藏测试不过 | 提示 token |
|---|---|---|---|---|---|
| 不交流 | 0（0/101） | 0.075 | 0 | 0.375 | 492k |
| 本方法（random:16） | 0.010（1/102） | 0.083 | 0 | 0.625 | 441k |
| 本方法，换成别人的帖子 | 0.030（3/99） | 0.117 | 0 | 0.700 | 432k |
| 文字：作者的汇报 | 0.482（54/112） | 0.483 | 0.05 | 0.825 | 335k |
| 文字：直接贴代码和测试日志 | **0.679**（74/109） | **0.633** | **0.25** | **0.300** | 577k |

- 本方法和换帖对照、不交流没有区别。这是在论坛里的第三次复核，和 R13 更正、R14 一致；282 + 620 次带 latent 的生成都没有退化。
- 绕过作者的嘴、直接贴产物，比作者自己的汇报多传过去 0.20，整个类做对的比例从 0.05 升到 0.25，代价是 1.7 倍的提示 token。
- 两种文字帖子里，诚实的 agent 只在可见测试通过时才说 DONE。可见测试不检查格式，所以"宣布完成但隐藏测试不过"是作者自己也相信的不实说法。贴产物时，这个比例从 0.825 降到 0.300。消费者的尝试也更多（PARTIAL 168 次，汇报时 79 次），说明它们更常发现自己没写对。
- 这对零信任是一个干净的文本基线：最好的核对证据目前是产物本身，它准，但贵。任何 latent 证据都要和"贴产物"比准确率和代价，而不只是和作者的汇报比。

**R16　KV 帖子：把作者手里的 KV cache 当帖子，读者能读出内容；作者说谎时，读者跟着作者的代码走，不跟着作者的话走。**（作业 24520441；离线测量，每格 40 个合成项目；`model/kv_posts.py`）

帖子就是作者写完汇报时的 KV cache，读者的提示接在它后面生成。作者上下文平均约 470 个位置。`snap:B` 每层每个 KV 头只留 B 条：作者汇报的注意力最集中的位置，外加最前面 4 个位置（attention sink）。

| 作者的话 | 帖子 | 消费者通过率 | 代码里是真标签 | 代码里是作者说的假标签 | 帖子大小 |
|---|---|---|---|---|---|
| — | 不交流 | 0 | 0 | — | — |
| — | 贴代码（文字） | 0.53 | 0.98 | — | 0.3 KB |
| 如实 | 文字 | 0.71 | 0.85 | — | 0.1 KB |
| 如实 | KV 整份 | **0.94** | 0.96 | — | 66 MB |
| 如实 | KV snap:256 | 0.88 | 0.99 | — | 37 MB |
| 如实 | KV snap:64 | 0.34 | 1.0 | — | 9 MB |
| 省略 | 文字 | 0.01 | 0 | — | 0.1 KB |
| 省略 | KV 整份 | **0.96** | 0.96 | — | 66 MB |
| 省略 | KV snap:256 | 0.51 | 0.98 | — | 37 MB |
| 省略 | KV snap:64 | 0 | 0 | — | 9 MB |
| 说错 | 文字 | 0 | 0 | **0.88** | 0.1 KB |
| 说错 | KV 整份 | **0.86** | 0.96 | **0** | 66 MB |
| 说错 | KV snap:256 | 0.74 | 0.99 | 0.01 | 37 MB |
| 说错 | KV snap:64 | 0.21 | 0.85 | 0 | 9 MB |

移植对照（把别的项目的 KV 帖子给读者）：通过率为 0，读者代码里出现那个项目标签的比例，整份 0.43、snap:256 0.46、snap:64 0.91。内容确实来自帖子。

- **KV 帖子能传内容**，这是 soft-token 帖子（R13 更正、R14）做不到的。整份 KV 在三种说法下都超过作者自己的文字。
- **作者省略时，KV 帖子会泄露作者没说的东西**：文字 0.01，整份 KV 0.96。
- **作者说谎时，读者跟着作者的代码走**：文字有 88% 照着假标签写；整份 KV 里同时有真代码和假说法，读者 96% 用真标签，0% 用假标签。只留 64 条时也有 85% 用真标签。
- **按汇报注意力挑出的条目，带的是作者说话时想到的东西。** 只留 64 条时，作者如实或说谎，标签都在（1.0 / 0.85），因为汇报谈到格式时会看向代码里的标签；作者省略时标签就不在（0），因为汇报没往那里看。64 条时通过率低，主要丢的是字段顺序：标签和分隔符都在。
- **代价**：整份 KV 帖子 66 MB，文字帖子平均 124 字节，相差五十多万倍。读者省掉的是重新 prefill，传输和存储都贵得多。
- **整份 KV 在计算上等价于把作者的整段上下文拼到读者前面**（单元测试逐 token 检查过），所以它的优势不能算在"隐式"头上，要和同样内容的文字比。

- **挑哪些条目很重要**：同样 64 条，按汇报注意力挑出的那组带着标签，均匀挑和只留最后 64 条都带不出。256 条时，snap 在如实和说错下比 uniform 高 0.3 到 0.4，省略时两者一样（0.51 对 0.49）。也就是说，汇报没谈到的东西，snap 并不比随便挑更好。
- **只留汇报本身的 KV（recent），行为像文字**：说错时 39% 跟着假标签。按汇报注意力挑的 KV 则 0% 跟假标签、85% 用真标签。两者大小相同，差别只在挑了哪些条目。

**R17　负载：分别写的 KV 帖子放在一起就读不了（不可组合）；一起编码、或写成文字都没问题。**（作业 24538551 任务 4–6；只有一条是读者的生产者发的，另外 M − 1 条来自别的项目，顺序随机，每条标明类名）

| M | 文字汇报：如实 / 说错 | 汇报 + 代码：如实 / 说错 | KV 整份：如实 / 说错 | KV snap:256：如实 / 说错 |
|---|---|---|---|---|
| 1 | 0.68 / 0 | 0.83 / 0.19 | **0.98** / **0.85** | 0.86 / 0.78 |
| 4 | 0.63 / 0 | 0.83 / 0.11 | 0.19 / 0.16 | 0.11 / 0.09 |
| 16 | 0.33 / 0 | 0.36 / 0.03 | 0 / 0.01 | 0.01 / 0 |

- 只给一条时 KV 最好，四条时就降到 0.19，直接问时也只有 40% 答对。文字在四条时几乎不变，十六条时才明显下降。
- 这些 KV 帖子是各个作者分别算的，依次接在一起，彼此从没互相看过；每条都以同样的系统提示开头，各带一组 attention sink。并行编码（APE、CacheBlend、TurboRAG）的文献报告过同样的退化。
- **两种免训练的修法都没用**（作业 24540564）：只保留一份共同的系统提示，帖子首尾相接，M = 4 时如实 / 说错为 0.15 / 0.15；都放在原来的位置（并行，做法同 APE 但不调注意力温度），为 0.16 / 0.11。M = 16 时都接近 0。
- **同样的会话写成文字就撑得住**：M = 4 时 transcript 为 0.81 / 0.76，M = 16 时为 0.31 / 0.28；作者说错时，读者仍然 0% 用假标签。
- **诊断（作业 24542581）：问题出在"分别编码"。** 把 4 段会话一次性一起编码成 KV，如实 / 说错为 0.85 / 0.80，说错时 100% 用真标签、0% 用假标签，和 transcript 文字一样好。同样的 4 段会话分别编码后接起来只有 0.15。**单条 KV 帖子读得很好，几条分别写的 KV 帖子放在一起就读不了**：它们彼此从没互相看过，读者没法把它们拼起来用。文字没有这个问题，因为读者 prefill 时会把它们一起重新编码。

- **读错的方式是"特征串台"**：4 条帖子时，读者代码里 60% 用的是别的帖子的标签，而且偏向最后一条（160 次里 66 次选了最后一条）。读出来的记录是完整的，例如 BookCatalog 的读者写出 `'BOCJ#1965#Herbert#Dune'`：字段和顺序是自己的，标签却是 OrderLog 那条帖子的。所以读者读得出内容，只是没法把内容和它属于哪条帖子绑在一起。
- **加明文出处也救不回来**（作业 24543427）：每条帖子后面接一句由读者 prefill 的标注（谁写的、关于哪个类），4 条时为 0.18 / 0.15。只有一起编码（后来的帖子能看到前面的帖子）才能绑定。
- **基准的一个缺陷**：SecretBench 只有 8 种类名，M = 16 时每个类名出现两次，连文字也无从区分，所以 M = 16 那一行不能用来比较。
- **M = 8（类名互不相同）与 M = 2**（作业 24545121）：

  | M | 文字汇报：如实 / 说错 | transcript 文字：如实 / 说错 | KV 分别编码：如实 / 说错 | **KV 一起编码（共享流）**：如实 / 说错 |
  |---|---|---|---|---|
  | 1 | 0.68 / 0 | 0.83 / 0.78 | 0.98 / 0.85 | 同左 |
  | 2 | — | — | 0.39 / 0.39 | **0.86 / 0.80** |
  | 4 | 0.63 / 0 | 0.81 / 0.76 | 0.15 / 0.15 | **0.85 / 0.80** |
  | 8 | 0.60 / 0（97.5% 用假标签） | 0.74 / 0.81 | 0.05 / 0.01 | **0.78 / 0.76** |

  一起编码时，说错的情况下读者在所有 M 下都 100% 用真标签、0% 用假标签。分别编码的 KV 从两条帖子起就开始串台。
- 对"一大群 agent"来说这是决定性的：一个思维论坛必须能同时读很多条帖子。一起编码有一个自然的论坛形态：**只追加的共享潜在流**。每个作者把自己的会话写在论坛已有 cache 的后面，帖子之间天然能组合；每条帖子只编码一次，而不是每个读者各编码一次。它在准确率上等同于把所有会话写成文字放在读者前面，好处在计算上：读者不必重新 prefill 任何帖子。这也解释了 LatentMAS 为什么能用：它沿着一条链传递工作记忆，本来就是一起编码。
- 已接入论坛：`--channel stream`（`model/kv_posts.py` 的 `KVStream`）。读者拿到的是它所选帖子在流里的那几段，其余部分就像被逐出了 cache。论坛实验在作业 24548747（E0st）。

- 共享潜在流在论坛里能用，也抗住了全员说谎；分别编码的 KV 帖子做不到这一点（R17）。
- **但它的好处来自"分享作者的工作现场"，不来自"隐式"**：同样的会话写成文字，通过率没有可测的差别（这个样本量下，差距的置信区间是 −0.10 到 +0.06）。隐式信道剩下的可能优势在代价上（读者不必重新 prefill），这还没有测。
- 同一设定下"换段"对照和"全员说错 + 会话文字"没有跑完：作业 24548747 任务 0 的第二个条件显存溢出（每个项目的流没有及时释放，已修复），重跑的作业被我在改基准前取消了。这两个条件会在新的、规模更大的实验里一起跑。

**2026-10-19：基准做实，按统计功效重做。** R10–R18 用的 SecretBench 太简单：只有 8 个固定领域，类名和样例值反复出现；每个项目只有一个生产者和三个只需解析字符串的消费者；没有哪个方法真的需要同时读两条帖子；每格 40 个项目、一个种子，也没有置信区间。

SecretBench 已经原地升级，具体设计见 `benchmark.md`：
- 每个项目两个生产者、五个消费者，其中 `migrate` 需要两条帖子；
- 格式多了补零位数和校验码；
- 前 320 个项目类名互不相同，字段和取值都随机。

离线测量改为每行一个（项目，消费者，种子）条目；`analysis/stats.py` 给出按项目聚类的 bootstrap 置信区间和配对 McNemar 检验。依赖旧生成器的脚本和分析已经删除，旧结果的代码在提交 b4d81db。

**R19　共享潜在流里，单独读一条不在开头的帖子要带上流的 attention sink，否则几乎读不出。**（离线测量，作业 24556489 修复前的 stream 任务；诊断作业 24564850）

在 `offline.sh` 里，每个项目的两条生产者帖子按随机顺序写进同一条流。只需要一条帖子的消费者只拿到流里的那一段，其余部分视同被逐出。按"所需帖子在流里排第几段"拆开看（作者如实，种子 0–1，每格约 200 个条目；诊断为 60 个项目，每格 30 个）：

| 消费者 | 所需帖子是第 1 段 | 是第 2 段，原来的读法 | 是第 2 段，带上流开头 4 个位置 | 是第 2 段，带上它前面的整段流 |
|---|---|---|---|---|
| decode | 0.74 | **0.10** | 0.73 | 0.67 |
| read_export | 0.85 | **0.07** | 0.90 | 0.93 |

- 流里的第 2 段是在第 1 段之上编码的，单独拿出来时既少了它看过的上文，也少了整条流开头的那几个位置。补回开头 4 个位置（attention sink，StreamingLLM 的做法）就恢复到第 1 段的水平；把前面的整段流都补上，并不更好。所以坏的是 sink，不是上文。帖子之后留下的位置空档（被逐出的后续帖子）没有影响。
- 修复：`KVStream.prefix` 总是带上流的前 4 个位置（提交 163d5cd）。60 个项目上整体通过率从 0.32 升到 0.50。
- R18 的论坛实验用的是修复前的读法，却没有出现这种崩塌。一个可能的解释是：论坛里读者能看到的帖子常常包括流里的第 1 条，sink 也就随之带上了。这只是推测，没有单独验证。
- 修复前的 stream 结果已移到 `runs/diag_stream/`。

**R20　基准的一个混杂：读者常常不听"不得调用其他方法"，而听不听随信道而变。**（离线测量，作业 24556489，3 个种子 × 200 个项目，stream 以外的信道全部跑完）

SecretBench 的消费者单独测试时，其他方法都是会抛异常的桩，这是为了堵住"委托给参考实现"的漏洞。题面也写明了它必须自己处理格式。但读者常常还是去调 `self.decode`、`self.export` 这类方法，这样的代码不管读者知道多少都必然失败。下表是第一次作答时调用了不该调用的方法的比例，括号里是不委托的那部分的通过率：

| 信道 | decode | get_field | migrate |
|---|---|---|---|
| 完整规格 | 0.00 (0.49) | 0.05 (0.35) | **0.99** (0.17) |

### E0：MVP 测量（设计；已于作业 24332670 完成）

- **任务**：ClassEval 中 77 个经两次复验的类，其中 70 个有 ≥3 个方法。每个方法是一个子任务；隐藏测试做评测，第 1 个用例作为可见测试。3 个 agent，无角色。
- **条件**：
  - 信道：none / text / latent（report 或 artifact）；
  - latent 的对照：none / shuffle / zero；
  - 信任：blind / attested；
  - 篡改：1/3 的 agent 把 DONE 篡改为真（`overclaim_mode=always`）。
- **指标**：
  - `method_pass`、`class_pass`；
  - `false_declaration`：团队宣布完成，但隐藏测试不过；
  - `false_done_rate`；
  - 传播：读过“依赖方法的虚假 DONE”的尝试，与其余尝试相比的通过率；
  - 询问：`anchor` / `verified` / `claim` 三问的准确率，与“拿别人帖子回答”的基线比较；
  - `overclaim.reveals_fail`；
  - 成本：token 数、载荷大小。
- **预注册假设与判读**：
  - **H1（传播）**：blind 下 `false_declaration` 显著大于 0，且 misled 组的通过率低于 clean 组。成立即构成卖点一。
  - **H2（零信任）**：attested 能把 `false_declaration` 压到接近 0，`method_pass` 上升；代价是更多轮次和 token。
  - **H3（内容）**：免训练 report-latent 在 shuffle 和 zero 对照下与无对照**无显著差别**。这是预期中的阴性结果，与 deng2026close 一致，为 E1 的训练提供动机。
  - **H4（真实状态）**：如果 report-latent 的 `reveals_fail` 显著高于 text 和 baseline，就支持“latent 带出真实状态”；不成立则说明免训练载荷带不出真实状态。两种结果都要报告。
- **资源**：smoke 测试约 1 小时，用 1 个 3g.40gb MIG 实例。E0 是 4 个数组任务，各不超过 8 小时，具体用时要根据 smoke 的耗时重新估算。

## 5. 现象与风险

**故事（2026-10-18 更正后）.** 文字是一个有损、而且可以撒谎的接口。零信任要求看到说法后主动核对。我们从作者的上下文里读出 k 个向量附在帖子上，拿一个信息量已知的基准去测，看到的是：这些向量带着作者所知的状态，但冻结的读者读不出其中的内容。

| 现象 | 证据 | 状态 |
|---|---|---|
| **帖子跟随作者所知，而非所言**（状态层面）：作者谎称"做完了"时，latent 仍带着真实的测试结果 | R8：探针区分谎言与真话 0.91，只看文字 0.71；R12：训练过 writer 后，原版读者在说谎的帖子上读出真实 CI 0.94，换帖对照 0.48 | 成立。这是 latent 作为"核对证据"的依据 |
| **冻结读者读不出 latent 里的实例内容**：免训练的两种写法都不行，附在文字旁边也不改变读者被文字带着走 | R2、R10：分块平均 0.008；R13 更正：未训练 gist 0.017–0.025；R14：说错时 84–93% 跟着文字里的假格式 | 成立（阴性结果）。原先的"读法比训练重要""用得出、说不出"已撤回 |
| **在任务上训练 writer，会收成模板** | R13：训练后格式规整、标签错误；E1s2 的变体也没有改善 | 成立 |
| **绕过作者的嘴的文本证据更准**：直接贴代码和测试日志，比作者的汇报传得更多，团队谎报完成也更少 | R15：跨 agent 通过率 0.68 对 0.48，宣布完成但不过 0.30 对 0.83，提示 token 1.7 倍 | 成立（单 seed）。这是 latent 证据要比的基线 |
| **KV 帖子能传内容，而且跟着作者所知走**：作者省略或说谎时，读者照样用真格式 | R16：KV 整份如实 / 省略 / 说错 0.94 / 0.96 / 0.86，说错时 0% 用假标签；移植对照为 0 | 成立。但作者的会话原文写成文字也一样（0.83 / 0.70 / 0.78），所以这是"分享工作现场"的效果，不是 KV 的 |
| **同样的内容，写成"汇报在前、代码在后"的消息，读者就被谎言带偏** | R16：0.20，会话原文 0.78 | 成立（单 seed） |
| **按作者汇报的注意力挑出的 KV，带的是作者说话时看着的东西**：包括谎言背后的真相，不包括省略掉的 | R16：64 条时真标签 如实 1.0 / 说错 0.85 / 省略 0；只留汇报本身的 64 条，说错时 39% 跟假标签；均匀挑 0 | 成立。这是目前唯一"隐式"特有的现象 |
| **分别写的 KV 帖子不可组合** | R17：4 条时 0.15（去重、并行都救不回），一起编码 0.85，文字 0.81 | 成立。对"一大群"是决定性的障碍 |
| **对文字消息，问得出 > 用得上**，信息越多差得越多 | R14 容量曲线：直接问时 100% 复述标签，代码里用上 73–85% | 初步 |
| 许多帖子同时在场时会怎样 | — | 待测（负载曲线） |

**次要但可写进论文的观察.**
- 文本的损失在读取精度，不在带宽（R11）：帖子写成示意串时成功率 0.31，只有文字描述时 0.15。
- 未经处理的 latent 会把读者带崩（R5，12–19%）；训练过 writer 后为 0（R12）。
- 连贯的谎言在文本里不留痕迹（R7）；同伴写的测试 77% 是错的（R9）。这两条来自文本信道，放在动机或附录。

**风险与局限.**
- **隐私**：帖子跟随所知，就会带出作者没写的东西。
- **审计**：探针和询问的结果都要配因果检验（移植、上下文编辑）；"用得出、说不出"的观察已撤回，不能再作为询问会漏报的证据。
- **受信推理**：如果 agent 能自己提交向量，就能伪造帖子。
- **证据还薄**：目前单 seed、单模型（Qwen3-8B），40–70 个项目，合成任务。第二个模型和多 seed 都在 §3.4 的清单里。
- **措辞**：虚报的主因是能力不足，而不是策略性欺骗（§0）。“欺骗”只用于作者被指示说错的情形。
