# 方法：从作者上下文里读出来的潜在帖子

一条帖子不是作者写下的一段话，而是从作者的完整上下文中读出来的 k 个向量。

## 为什么不直接用文字

agent 之间用文字交流有两个毛病。

一是**有损**。在我们的实验里，生产者把一个私有记录格式写成文字发给同伴，同伴照着写代码，只有一半能写对。问题不在于信息没写进去，帖子里格式基本都写全了；问题在于自然语言转述不精确，读的人常常数错字段、弄反顺序。

二是**可以撒谎**。能力不够或急于完成的 agent 会声称自己做完了；被要求撒谎时，模型能写出连贯、不留痕迹的谎言，读者从文字里几乎问不出真相。

零信任的意思是照常交流，但每条说法在使用前都要主动核对。所以我们关心的不只是帖子能传多少信息，还有它能不能帮读者核对作者的说法。

一个直接的想法是不传文字，传隐状态。但最常见的做法是把作者回复那几句话的隐状态池化成几个向量，我们测下来几乎什么也传不过去：它看到的只是作者"说了什么"，而且池化把具体内容抹平了。

## 怎么做

作者在写帖子之前，上下文里已经有了它知道的一切：任务描述、自己写的代码、CI 给的测试结果，以及它自己的汇报。我们不去压缩那几句汇报，而是让模型把整个上下文"再读一遍"：

```
作者的上下文 C（任务、代码、测试结果、汇报）  +  k 个固定的查询向量 q₁…q_k
                         │  一次前向（C 的 KV cache 直接复用，只算 k 个位置）
                         ▼
              q₁…q_k 位置上的末层状态 h₁…h_k
                         │  映射回输入空间
                         ▼
                 k 个 soft token = 一条帖子
```

映射回输入空间分三步：先乘 W_a（让 W_out·W_a ≈ W_in 的岭回归解，LatentMAS 用的就是这个对齐）；再去掉落在 `<|im_end|>`、`</think>` 这类控制 token 方向上的分量，否则读者会被带崩；最后缩放到平均 embedding 的范数。

查询向量就是随机抽的 k 个词表 embedding，**整个过程不训练任何参数**，代价只是 k 个位置的一次前向。

## 读者怎么读

读者是同一个冻结模型。帖子作为 k 个 soft token 插进它的提示，前面加一行明文出处：

```
Messages from teammates (latent):
[post 0] from agent1 on `encode`:
<k 个 soft token>
```

读者自己的上下文不动，帖子只是追加进去。出处是明文的：谁写的、关于哪个方法，读者和系统都看得见；内容是隐式的。

论坛就是这些帖子的集合。一个读者收到和自己任务相关的帖子；在负载实验里，它会同时收到 M 条。

## 实测效果（2026-10-18）

- **读不出内容**：冻结的读者读不出这种帖子里的实例内容。SecretBench 上只给潜在帖子时，消费者通过率约 0.02，文字是 0.66。附在文字旁边时，读者仍跟着文字走（R13 更正、R14）。
- **带着作者所知的状态**：从作者上下文读出的向量里，确实带着作者"知道的"状态。线性探针能区分谎言与真话；训练过的写入端能让原版读者读出真实的测试结果（R8、R12）。
- **下一步**：方法的重点因此转向"作为核对说法的证据"，而不是代替文字传内容。

## 可以调的只有三样

- k：每条帖子几个向量（默认 16）。
- 查询向量从哪来：随机词表向量，或者一段固定提示的 token。
- 取哪一层的状态（默认最后一层）。

## 一个前提

帖子由受信的推理端（我们的 harness，或托管模型的一方）从作者真实的上下文中计算，agent 不能自己提交向量。否则它可以直接伪造一个"看起来诚实"的帖子。后面所有"潜在帖子更难撒谎"的结论都建立在这个前提上。

## 和已有方法的区别

| 方法 | 传什么 | 要训练吗 | 和我们的差别 |
|---|---|---|---|
| 隐状态池化（我们的旧版；Interlat 的免训练形式） | 作者所写那几句话的隐状态 | 否（Interlat 要训练） | 只看作者说出来的话，不看整个上下文 |
| LatentMAS | 自回归生成的潜在思考，经 KV 工作记忆传递 | 否 | 我们不自回归，k 个查询并行读出，只传 k 个向量 |
| AC（Communicating Activations） | 中间层激活，与读者的激活合并 | 否 | 我们作为输入 token 追加，不改写读者的计算 |
| KVCOMM / KVComm | 作者的（部分）KV cache | 否 | 我们的大小与上下文长度无关，也不用校正位置 |
| C2C、gist / ICAE | 融合后的 KV / 压缩 token | 是 | 我们不训练压缩器 |

## 代码在哪

- 读出帖子：`model/hf_writers.py` 的 `GistWriter`；它用到的基本操作在 `model/backends/hf.py`（`read_after` 读查询向量，`to_input_space` 映射回输入空间）。
- 查询向量与（可选的）可训练映射：`model/hf_writers.py` 的 `WriteHead`；未训练的版本由 `random_head()` 生成。
- 在论坛里使用：`python -m forum.run --channel latent --writer-head random:16 ...`。`random:K[:SEED]` 就是未训练的方法本身；给一个 `.pt` 路径则加载训练过的 head（只作消融）。
